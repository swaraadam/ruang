## 2. Needs your decision

### Decision 1 — Agents cannot open PRs. This blocks all 28 issues. *(the one that matters)*

CLAUDE.md §7.5 makes "a PR opened against `main`" part of the definition of done for every issue,
and SETUP.md says "Agents open PRs; landing is always yours." But `.claude/settings.json` denies
`Bash(git push*)` **unconditionally** — not just pushes to `main`. So a feature branch can never
reach the remote, and the allowlisted `gh pr create` then fails:

```
pull request create failed: GraphQL: Head sha can't be blank, Base sha can't be blank,
No commits between main and p0-01, Head ref must be a branch (createPullRequest)
```

`gh pr create` does not push on its own, so its allow-list entry is unreachable. The *intent* of the
deny rule is right; it is written wider than the intent.

| Option | Trade-off |
|---|---|
| **A. Narrow the deny rule** to `main`/`--force` only, allow `git push -u origin <branch>` | Restores the intended workflow. Move the "never write `main`" guarantee to a GitHub branch-protection rule — server-enforced, which an agent cannot bypass, rather than an honour system. |
| **B. Keep the deny; you push** | No new agent capability, but a manual step before *every* issue. Unattended runs can then never hand you a reviewable artifact, only local branches. |
| **C. Redefine DoD** to "evidence + local branch, no PR" | Honest, but loses PR review, and CLAUDE.md §7.5 and SETUP.md both need editing. |

**Recommendation: A, plus branch protection on `main`.** Tonight's work is on `p0-01` ready for you
to `git push -u origin p0-01` if you want it reviewable immediately (option B as a stopgap).

## Two findings from this run

### 1. A latent trap that fires on the very next issue — filed as #34

Not caused by P0-01, but exposed by it. `tsconfig.base.json` sets `module: ES2022` +
`moduleResolution: bundler`. Combined with the `type: module` + `exports` fields P0-01 adds, any
member with **more than one source file** emits imports node cannot resolve. Reproduced:

```
packages/protocol/src/index.ts   export { HELPER } from './helper';
emitted dist/src/index.js        export { HELPER } from './helper';   <- extensionless
node import                      ERR_MODULE_NOT_FOUND
tsc -b exit 0   |   pnpm verify exit 0    <- ships silently
```

Every member is a single file today, so nothing is broken. **P0-02 is `packages/protocol` —
multi-file, imported by everything.** `nodenext` turns it into a compile-time `TS2835`, two lines.

I did not apply it. `apps/web` builds under Vite, `apps/gateway` runs under node, and whether they
share one resolution base is a toolchain decision that shouldn't be made unattended. Filed as #34,
and **P0-02 now depends on it** — a follow-up P0-02 could start without is the same as no follow-up.

### 2. My own earlier evidence needed correcting

The reviewer reported `pnpm run verify` failing in the sandbox with
`TS2307: Cannot find module 'vitest'`, contradicting my green result. **The reviewer was right and
the cause was environmental, not the PR:** the installed `vitest@5.0.0` was missing its entire
`dist/`, so its declared `types` target did not exist. `pnpm install --force` re-linked the same
damaged store copy; `rm -rf node_modules` + `pnpm store prune` + `pnpm install` fixed it.

`pnpm run verify` now exits 0 with 28 tests and **`pnpm-lock.yaml` is unchanged**, so the sandbox
matches exactly what CI tested. CI was green on `9321229` throughout.

The lesson is in the gate definition already: **land on CI, never on a local re-run.** A developer
machine can be in a state that fails for reasons that have nothing to do with the change.
