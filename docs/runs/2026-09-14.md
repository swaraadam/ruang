## The M-15 finding — why the polling fix was not written

The owner asked for `review` to get M-14's `verdict()` + polling treatment. It was not written,
because the race it would fix is not there:

| PR | proof step duration | printed |
|---|---|---|
| #70 | 18:07:09→18:07:10 (**1s**) | `CHANGES REQUESTED … 6c312433f` |
| #72 | 18:11:30→18:11:31 (**1s**) | `CHANGES REQUESTED … d56eacb3e` |
| #71 | 18:15:25→18:15:26 (**1s**) | `CHANGES REQUESTED … b63b2e96d` |

The marker was present, SHA-bound, and found immediately. The 4–7 minutes the owner measured was
the **reviewer** step; the proof step then failed in one second on a genuine blocking verdict.

A race is not structurally available. `guardrails.yml` raced because it is a *separate* workflow
firing on `synchronize` to observe another workflow's output (that is M-14). The proof step in
`claude-review.yml` runs *after* the reviewer step *inside the same job* — it cannot start early.
Adding a 15-minute poll would delay every correct rejection by up to 15 minutes and invite a later
"fix" that reads an absent marker as a pass, which is the one failure the gate exists to prevent.

**What the 12–14 minutes actually was:** `claude-code-review.yml`, a *second* reviewer running the
generic `/code-review` plugin. It is allowed only `create_inline_comment`, so it can never emit a
marker, and it has no proof step — it reports **SUCCESS on every PR regardless of findings**. Its
check is named `claude-review`, adjacent to `review` and near-identical to the marker string
`claude-review: pass`. That always-green check is the real defect and is what made this look like a
race. Filed as [#73](https://github.com/swaraadam/ruang/issues/73); parked, because
`.github/workflows/**` is denied to agents by `.claude/settings.json`.
